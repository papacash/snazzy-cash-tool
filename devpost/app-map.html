SnazzyCash App Map

This small app answers one question: is this purchase price fair compared with bundled sample prices, and what should the owner say next?

What the app is doing

The user picks a category, enters the vendor and item, chooses whether they are a loyal customer or a new customer, and submits the price. The app compares that against category sample prices and shows a win/loss result with a plain-language talking point.

Reference route

1. Fill in the form

Open src/app/page.tsx and look at the form state, category list, category-switch reset, and submit handler.

2. Trace the calculation

Follow the pricing logic in the same file: office-supply totals become per-unit prices, while software/subscription prices become monthly per-seat equivalents before the sample-range comparison.

3. Watch the result render

See how the summary panel updates from the methodology state to the rendered score, badge, and next-step message.

To change this, start here

  • Change the fairness logic in src/app/page.tsx if you want a different score behavior.
  • Change sample ranges and their comparison basis in src/data/pricing-data.json if you want different category baselines.
  • Change the styling in src/app/globals.css if you want the UI to feel more premium, more playful, or more minimal.

Practice to reuse

Use a visible acceptance criterion, then trace the exact code path that produces it. In this app, “a valid submit shows a win/loss result” was the key behavior, and the implementation and verification both lived in the same screen. This is a good pattern for future agent-assisted builds: define the observable outcome first, then prove the code path that creates it.
